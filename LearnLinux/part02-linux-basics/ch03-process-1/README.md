## 1. 进程与 fork：一分为二

进程是"正在运行的程序"：它有自己的地址空间、打开的文件（上一章的 fd 表）、以及一个全系统唯一的编号 **PID**；生它的进程叫父进程，编号 **PPID**。创建新进程的方式朴素得惊人——`fork()` 把当前进程**复制一份**：

```cpp
pid_t pid = fork();
```

一次调用，却在两个进程里各返回一次：父进程拿到**子进程的 PID**（正数），子进程拿到 **0**；失败则父进程得 -1。代码从此分叉，靠返回值认领身份。`ex01_fork_basic.cpp` 实测（PID 每次运行都不同，看关系不看数值）：

```
before fork: pid = 3211
parent: my pid = 3211, my child = 3212
child : my pid = 3212, my parent = 3211
```

父子从 fork 的下一行起跑同一份代码、初始数据一模一样（包括变量当时的值），之后各过各的、互不影响——子进程改变量，父进程的那份纹丝不动。内存上内核用**写时复制**（Copy-on-Write）偷工：先共享同一批物理页，谁真改了才给谁复制。子进程继承的东西要记一笔：**fd 表会继承**（上一章伏笔：open 的文件在子进程里同样开着），内存映像、变量值、当前目录、环境变量也都继承；不继承的是 PID、PPID、未决信号等"身份"信息。

还有一个和上一章呼应的坑先在这里点破：fork 连 **stdio 的缓冲区**都复制。`ex01` 里 fork 之前特意 `fflush(stdout)`——因为若"before fork"那行还躺在缓冲里没冲出去，子进程的缓冲里也有一份，父子各自退出冲刷时它会在输出里出现**两次**（重定向到文件时缓冲更大、更容易中招；实测已验：不冲刷时管道输出里这行计数为 2，加了 fflush 后为 1）。规矩：**fork 之前先 fflush，或者子进程里只用 write 系统调用说话**。

## 2. exec：同一个进程，换一套映像

fork 造的是"自己的分身"；想让子进程去干**别的程序**的活，要用 exec 家族（`execl`、`execv`、`execvp` 等，区别在参数传递与是否查 PATH）。exec 把当前进程的映像整体替换成新程序——代码、数据、栈全部换新，只有 PID 和（大部分）fd 还在。两个推论必须刻住：

- **exec 成功，绝不返回**。能执行到 exec 的下一行，必然是它失败了（所以其后紧跟 perror + 退出是标准写法）；
- 旧映像里**没冲刷的 stdio 缓冲随映像一起消失**。

`ex02_fork_exec.cpp` 用两行"永远看不见的打印"实测了这两点，全部输出只有：

```
hello from exec
parent: child finished
```

子进程里 exec 之前那句无换行的 `printf` 躺在缓冲里、随映像替换蒸发；exec 之后那句 `printf` 则根本不在新映像的执行路径上。fork+exec 是 Unix 造进程的经典两段式：fork 决定"生"，exec 决定"成为谁"——shell 运行每条命令、服务器接客派生子进程，用的都是这套组合拳。

顺带交代子进程退出用哪个函数：`exit()` 会冲刷 stdio 缓冲、执行 atexit 以及（对 C++ 局部对象以外的）收尾动作，而 **`_exit()` 立刻进内核，什么都不冲**。fork 之后的子进程若走 `exit()`，继承来的缓冲副本会被再冲一遍（第 1 节的重复打印还有这条成因）；子进程收尾的纪律是：**有自己要冲刷的内容先手动做完，然后 `_exit`**。ex02/ex03/ex04 里子进程一律用的 `_exit`。

## 3. wait 与退出状态解码：父进程的收尸义务

子进程结束时，它的退出码会被内核暂存，等父进程来取。**在父进程取走之前，子进程的进程表项不能释放**——这就是下一节僵尸的成因。`wait(&status)` 等待任意一个子进程结束并回收；`waitpid(pid, &status, 0)` 可以指定等谁。取回的 `status` 是个**位段**，不是普通整数，必须用宏解码：

- `WIFEXITED(status)`：是否正常退出；是，则 `WEXITSTATUS(status)` 是退出码（0~255）；
- `WIFSIGNALED(status)`：是否被信号所杀；是，则 `WTERMSIG(status)` 是信号编号。

`ex03_wait_status.cpp` 两幕实测：

```
child 3219: exited = 1, code = 42      ← _exit(42) 的子进程
child 3220: signaled = 1, sig = 15     ← 给自己发了 SIGTERM 的子进程
```

记住分工：**正常结局看退出码，异常结局看信号**。一个进程"返回了 1"和"被 9 号信号打死"是完全不同的事故等级，排障时先用这两个宏定性。

## 4. 僵尸与孤儿：两种"身后事"

**僵尸（zombie）**：子进程已经结束、父进程迟迟不 wait。它不再运行、不占内存，只剩进程表里一个表项（PID、退出码、资源统计），状态标为 Z。`ex04_zombie_orphan.cpp` 第一幕故意制造一只（子进程立刻退出、父进程睡 10 秒不回收），窗口期内 `ps` 实测：

```
PID STAT CMD
3223 Z    [ex04_zombie_orp] <defunct>
```

危害要说清：单个僵尸几乎无害，但**父进程若批量造子进程又从不回收，僵尸会堆满进程表**，新进程 fork 不出来——长跑服务器的经典死法之一。消灭方法只有一个：父进程 wait。（给父进程发 SIGKILL 也行——父进程没了，僵尸转归下面这位收养。）

**孤儿（orphan）**：父进程先结束，子进程还活着。内核把它的 PPID 改挂给 **PID 1**（或最近的 subreaper 进程），由这位"大家长"负责在它结束时回收——所以孤儿不危险，归宿有人兜底。`ex04` 第二幕实测：父进程退出后，子进程醒来报告 `my new parent = 1`。

一组对照收尾本章：僵尸是"死而未葬"（等父进程收），孤儿是"生而无父"（系统收养）。下一章我们会把进程再往深处看：进程组、会话、以及常驻后台的标准形态——守护进程。

## 示例代码：构建与运行

```bash
cd examples
cmake -S . -B build
cmake --build build
./build/ex01_fork_basic
./build/ex02_fork_exec
./build/ex03_wait_status
./build/ex04_zombie_orphan     # 配合另一终端的 ps 观察，约 12 秒
```

核对要点：

- `ex01`：before fork 只出现一次（管道里计数亦为 1）；子进程打印的 parent 与父进程的 pid 相同；父子行顺序可交换。
- `ex02`：输出只有 echo 的一行与父进程一行；子进程的两句 printf 都不出现。
- `ex03`：第一幕 exited=1、code=42；第二幕 signaled=1、sig=15。
- `ex04`：僵尸窗口内 ps 显示状态 Z 与 `<defunct>`；父进程回收后僵尸消失；孤儿打印的新 PPID 为 1（或本机 subreaper 的 PID）。

> 验证记录：以上结果由作者在 Ubuntu 24.04 / GCC 13.3 环境下以 `-std=c++11 -Wall -Wextra` 构建实测（零警告），僵尸状态经运行窗口内 ps 实测，日期 2026-10-22。
