## 1. mutex：把读-改-写圈成临界区

互斥锁的语义只有一句：**同一时刻只允许一个线程持有**。被锁保护的代码段叫**临界区**。第 1 章的病根是 `++counter` 的读-改-写三步可以被别的线程插队；把这三步圈进临界区，插队就无从发生——`ex01_mutex_counter.cpp` 与第 1 章 ex05 同一份活，只多了一把锁：

```
mutex counter = 1000000 (expected 1000000)      ← 次次精确，不靠运气
```

圈临界区有两条纪律，背下来：

1. **同一份数据，永远同一把锁**。锁保护的不是代码，是数据；两处代码摸同一变量却用两把锁，等于没锁（练习 1 的坑）。
2. **临界区只圈共享数据的操作**，不圈无关计算、日志输出、网络 IO——圈得越大，并行度越低（第 3 节用数字说话）。

`std::mutex` 本身的 `lock()/unlock()` 几乎永远不要直接调用，原因在下一节。

## 2. RAII 锁：lock_guard 与 unique_lock

C++ 的答案还是 RAII：锁的获取写在锁对象的构造里，释放写在析构里。于是**任何**离开作用域的路径——return、break、异常——都必然解锁。`ex02_raii_locks.cpp` 的核心演示就是异常路径：

```cpp
static void addThenThrow(long n) {
    std::lock_guard<std::mutex> lk(g_m);
    g_total += n;
    throw std::runtime_error("boom");   // lk 在栈展开时析构，锁照样释放
}
```

主线程捕获异常后还能继续读到 `total after exception path = 42`——若是手工 `lock(); ...; unlock();`，异常一抛，unlock 永远执行不到，后面所有碰这把锁的人集体挂死。这种 bug 在评审时极难看出来，所以纪律是：**裸 lock/unlock 不进代码库**。

两个 RAII 锁的分工：

| | lock_guard | unique_lock |
|---|---|---|
| 能力 | 构造上锁、析构解锁，仅此而已 | 可延迟上锁（defer_lock）、中途解锁/再锁、可转移、可带超时（配 timed_mutex） |
| 成本 | 最轻 | 略重 |
| 必选场景 | 简单临界区（默认选它） | 条件变量的搭档（下一章）、两段式临界区 |

ex02 后半段演示了 unique_lock 的两段式：锁内只取快照 → 解锁 → 锁外做昂贵计算（翻倍）→ 再上锁提交，`final total = 84`。昂贵计算不占着锁，是缩小临界区的标准手法——lock_guard 做不到中途放手，这就是选 unique_lock 的时刻。

## 3. 锁的开销：ex04 的三档实测

同一份 100 万次累加，三种策略在作者环境（2 核 VM）实测：

| 策略 | 结果 | 耗时量级 |
|---|---|---|
| 不加锁 | 短缺（24 万~87 万不等），**偶尔也恰好 1000000** | 2~3 ms |
| 粗锁（一把罩全程） | 精确 | 约 3 ms |
| 细锁（每次累加一把锁） | 精确 | 34~134 ms |

三条教训：

- **无锁的错误结果不可复现**，甚至偶尔全对——这比稳定出错更危险，它会让测试通过、让问题潜伏到线上。第 1 章验收对它就只敢断言上界。
- **细锁慢了一个数量级**，慢在两处：100 万次 lock/unlock 本身的开销，加上 4 个线程在同一把锁上高频争抢（抢不到就睡、醒了再抢，调度开销滚雪球）。
- **粗锁本题最快，但别误读**：它快是因为把活干成了串行——4 个线程排队各干各的 25 万次。真实业务里临界区中夹着不能串行的部分（如 IO）时，粗锁会把整个系统的吞吐压成单线程。

所以粒度之争的正解是：**先保证正确（锁住该锁的），再靠"缩小临界区 + 减少共享"优化**——分片（练习 4 把争抢摊到 8 把锁）、锁外计算（ex02 两段式），以及第 4 章的原子操作。不要反过来为了快先裸奔。

## 4. 读写锁：读者共享、写者排他

配置、字典、路由表这类数据的访问模式是**读多写少**：普通 mutex 会让读者也排队，纯属浪费。读写锁把锁分成两种拿法：

- 读锁（共享）：多个读者可同时持有；
- 写锁（排他）：写者独占，读者与其它写者都得等。

C++11 标准库没有读写锁（`std::shared_mutex` 是 C++17 的，专题时回访），本章用 pthread 的 `pthread_rwlock`。`ex03_rwlock.cpp` 的场景是一份配置 `(version, value)`，不变式 `value = version * 10`：写者整份更新 200 次，4 个读者高频读取并在锁外自查不变式。结果：

```
violations = 0                            ← 没有任何读者见过改一半的中间态
final: version = 200, value = 2000
```

写者更新的"两步"被写锁圈成原子整体，读者要么读到旧整份、要么读到新整份。两个使用注意：其一，读锁内只做拷贝、检查放锁外，缩短持锁时间；其二，读者太霸道时写者可能饿死——示例里读者每 1024 轮让行一次，glibc 的 rwlock 还可以用初始化属性改成写者优先，生产代码选哪种要看读写的时效要求。

## 示例代码：构建、运行与验收

```bash
cd examples
cmake -S . -B build && cmake --build build
./build/ex01_mutex_counter
./build/ex02_raii_locks
./build/ex03_rwlock
./build/ex04_lock_cost

bash tests/run_tests.sh
```

核对要点（与验收断言对应）：

- `ex01`：输出恰为 1000000，且重复运行永远精确；
- `ex02`：`caught: boom` 后仍能读出 42，两段式后 `final total = 84`（若锁在异常后没释放，程序会在 42 这步挂死）；
- `ex03`：`violations = 0`、`final: version = 200, value = 2000`；
- `ex04`：两种加锁策略结果精确；无锁版数值不定——你跑出的毫秒数与本书不同是正常的，看量级。

> 验证记录（测试先行）：验收脚本先行写定，首跑构建判红（passed=0）；实现后全绿（passed=5），复跑两次稳定，`-std=c++11 -Wall -Wextra` 零警告。ex04 耗时为作者环境（2 核）实测：粗锁约 3 ms、细锁 34~134 ms、无锁 2~3 ms 且结果不可复现（六次实测短缺 13%~76%，另有一次恰好全对——程序据此把判语改为动态生成，不让教材撒谎）。日期 2026-10-23。
