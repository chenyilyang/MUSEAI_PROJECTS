# 第 2 章 练习参考答案（第三部分）

## 练习 1

两处错误，正对应正文的两条纪律：

1. **同一数据两把锁**：`updateFromCan` 用 m1 保护 `g_cfg`，`readSnapshot` 却用 m2 —— 两把锁互不相认，A 写配置的半途 B 完全可以同时进来读，保护形同虚设。改法：一份数据全局只配一把锁，两处都用同一把（把 mutex 与数据放进同一个类/结构体、绑定声明，是防这种手滑的结构性办法）。
2. **临界区圈进了无关的耗时操作**：`renderReportToFile`（约 50ms 的文件渲染）被圈在锁内，它不碰共享数据（参数已是锁内拷贝？注意它读的仍是 g_cfg 本身——先在锁内把 g_cfg 拷贝到本地变量，解锁，再用本地副本渲染写文件）。原写法下每次 CAN 更新都要堵住所有读者 50ms。改法即正文的两段式：锁内只拷贝，快进快出。

## 练习 2

bug 在提前返回路径：`amount > g_balance` 时直接 `return false`，**漏掉了 unlock**。这把锁从此永远被"持有"，下一个调用 withdraw 的线程（包括自己再次调用）在 `g_m.lock()` 上永久挂死。潜伏性在于：余额充足时这条路径永不触发，功能测试全过；只有线上出现余额不足的取款时才爆，且爆点（挂死位置）离病灶（漏解锁处）很远，是最难查的一类并发事故。

RAII 改写：

```cpp
bool withdraw(long amount) {
    std::lock_guard<std::mutex> lk(g_m);
    if (amount > g_balance) return false;      // lk 析构，自动解锁
    g_balance -= amount;
    return true;                               // 同上
}
```

改后每条路径（正常返回、提前返回、乃至中间抛异常）的解锁都由 `lk` 的析构保证，与你写了多少个 return 无关——这正是"裸 lock/unlock 不进代码库"的理由。

## 练习 3

见 `ex03_safe_counter.cpp`（已编译验证：打印 1000000，退出码 0）。

要点：mutex 声明为 `mutable`，否则 const 的 `value()` 里锁不上（锁操作本身要改 mutex 的内部状态，const 方法默认无权改成员）；读方法 `value()` 同样要上锁——"只读"不等于"线程安全"，它读的仍是别人正在写的数据。封装的收益是调用方无从绕过锁：数据是私有的，手只能伸进带锁的方法。

## 练习 4

见 `ex04_striped_counter.cpp`（已编译验证：打印 1000000，退出码 0）。

快在哪：不同线程大概率落在不同分片、各锁各的，争抢概率约降为单锁的 1/8（4 线程更明显）；代价：一是 `value()` 要按序锁全部片（读变重、且必须守固定顺序防止与别的"多锁"代码死锁——第 5 章主题）；二是结构复杂、内存占用变大；三是分片数固定后线程数远超分片数时收益递减。另外注意哈希选片的分布依赖 thread id 的哈希质量，极端情况下几个热点线程撞同一片，收益会打折。

## 练习 5

(a) 必须 unique_lock 的场景：①**配条件变量**——`condition_variable::wait` 要求 unique_lock，因为等待期间要能解锁/再锁（下一章主角）；②**两段式临界区**——中途要显式 unlock 把昂贵计算放到锁外（ex02）；③**延迟/组合上锁**——先 defer_lock 拿到对象、稍后用 `std::lock` 同时锁多把，或需要把锁的所有权转移给别的函数/线程时。

(b) ex04 的粗锁临界区里只有纯计算，串行化的代价恰好被"零上锁开销"掩盖。生产临界区常夹着不能并行的慢操作：设想临界区里有一次 20ms 的磁盘写入或网络往返，粗锁意味着所有线程在这 20ms 里全体排队——4 个线程的有效吞吐直接回到单线程水平，且尾部延迟被最慢的操作放大。锁的粒度应该跟着"共享数据的操作"走，而不是跟着函数走：能挪出临界区的（拷贝后在锁外处理、IO 前先解锁）都挪出去，粗锁罩全程只是最后的选择。

(c) 读写锁的管理本身更贵：它要维护读者计数与等待队列，一次上锁的固定开销大于普通 mutex；写频繁时，写者每次都要等所有在读的读者退出、且写者持有期间读者全堵，"读者并行"的收益窗口被写操作切得稀碎，净效果是付了更贵的上锁成本却没换到并行度。此外读者源源不断时写者还可能饿死，需要额外的公平性策略。一般经验：读:写比不到 10:1 左右，先想普通 mutex 或缩小临界区，别急着上读写锁——用 ex04 的方法实测你自己的场景再定。
