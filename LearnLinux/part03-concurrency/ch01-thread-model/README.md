## 1. 线程：同屋檐下的执行流

线程是进程内部的执行流。同一进程的线程**共享**地址空间（全局变量、堆、打开的 fd 都是同一份）、**独占**自己的栈与寄存器（包括指令指针）。对照第二部分：fork 造的是"分家"——地址空间从此隔离；开线程是"同屋加人"——东西全摆在明面上，谁动了大家都看得见。这一字之差决定了并发编程的全部甜头与麻烦：通信免费（写个变量对方就看见），协调昂贵（同时伸手就打架，第 5 节立账）。

C++11 起标准库自带 `std::thread`，Linux 上它底层就是 pthread。构造即开跑：

```cpp
std::thread t(函数或可调用对象, 参数...);
```

每个线程有自己的 id（`std::this_thread::get_id()`）。`ex01_thread_basics.cpp` 让 4 个 worker 各算一段阶梯和，**各写各的槽位**，主线程 join 后统一打印：

```
slot 0 = 55
slot 1 = 210
slot 2 = 465
slot 3 = 820
```

验收还断言了 4 个 worker 的 id 两两不同、且都不同于主线程——线程是真·并行实体，不是函数的别名。注意示例里连 id 都先存进槽位、由主线程统一打印：让每个线程自己 printf，输出就会互相穿插（这本身是竞争的一种，见第 5 节）。

## 2. 参数传递：默认是拷贝，引用要表态

`std::thread` 的参数传递有个必须刻住的本质：**参数先被衰变拷贝（decay-copy）进线程内部存储，再以右值交给线程函数**。所以：

- 传普通值：线程函数拿到的是副本，改它与原变量无关（`ex02` 第一式：线程里把副本改成 99，原值仍是 1）；
- 线程函数签名是引用时，**必须用 `std::ref` 把实参包起来**送进去，否则编译都不过——这不是刁难，是逼你亲口承认"这个变量要被另一个线程动"（第二式：原值变为 99）；
- 传指针：指针本身是拷贝，但指向物是共享的（第三式：原值变为 7）。

一句话：**共享必须显式**。`ex02_args_and_ref.cpp` 的三行输出就是三种语义的判决书。另外提一句 lambda 捕获：按引用捕获 `[&]` 与 std::ref 是同一件事的两种写法，生命周期责任也一样——被捕获变量必须活得比线程久（练习 2 专练这个雷）。

## 3. 生命周期：join、detach 与 terminate 纪律

`std::thread` 对象是线程的"遥控器"，它有一个状态叫 **joinable**：只要它还代表一个活着的（或已结束但还没回收的）线程，就是 joinable。两条回收路线：

- `join()`：等线程跑完并回收，之后 joinable 变假，对象可安全析构。想要线程的**结果**，就必须 join（或通过共享变量/future 等通道，见第 6 章）；
- `detach()`：与线程脱钩，它从此自生自灭；对象不再 joinable、可安全析构，但你也**永远等不到它、拿不到结果**，还得保证它用到的一切活得比它久。

没选任何一条就析构对象会怎样？标准的选择是当场 `std::terminate`。反例 `bad_01_forgot_join.cpp` 实测：

```
leaving scope without join/detach...
terminate called without an active exception   （进程 abort，退出码 134）
```

为什么这么狠？因为"隐式 join"会让析构耗时不可预测，"隐式 detach"会留下访问已销毁对象的野线程——标准宁可炸在当场，也不让你带着时炸弹往前走。这与第 1 部分 RAII 的世界观一脉相承：**资源的释放方式必须显式表态**。`ex03_lifecycle.cpp` 把 joinable 的 1→0 与 detach 后线程独立干完活各演示了一遍（验收逐项断言）。

## 4. pthread 对照：手动挡的样子

在没有 std::thread 的 C 接口与老代码里，pthread 是原形：

```cpp
pthread_create(&th, NULL, worker, arg);   // worker 签名：void* (*)(void*)
pthread_join(th, &ret);                   // 等待并取回返回值（void*）
```

`ex04_pthread.cpp` 让工作函数把结果（42）放堆上、经返回值交回主线程。对比观感：std::thread 帮你把参数打包、类型检查、RAII 都做了；pthread 是"一个 void* 塞一切"，灵活但全靠自觉。看懂这一层，读车载中间件里的老 C 代码与某些 RTOS 移植层就不怵了。还有一个继承自进程世界的细节：线程的返回值/参数内存归属要自己记账（谁 new 谁 delete），ex04 里主线程 delete 了 worker new 的结果。

## 5. 竞争初瞥：先立账，下一章还

`ex05_race_glimpse.cpp` 把同一份活干两遍：4 个线程各对同一个普通 `long` 累加 250000 次，应得 1000000。实测四次的结果：

```
shared counter = 799360 / 819639 / 509958 / 634065   （每次都不同，全部短缺）
separate total = 1000000                            （各加各的，分毫不差）
```

原因一句话就能说清：`++counter` 是**读-改-写三步**，不是原子操作——两个线程同时读到 100、各自写回 101，两次累加只涨了 1。丢了多少取决于调度，所以每次不同。这就是**数据竞争**，它在 C++ 里不只是"结果不准"，而是未定义行为。本章的应对就是 ex01 的分槽：**不共享，就没竞争**。但真实系统里共享常常躲不掉（计数器、队列、缓存）——下一章的 mutex 就是为此而来，第 5 章我们还会用 TSan 把这段代码的 경쟁抓个现行。

## 示例代码：构建、运行与验收

```bash
cd examples
cmake -S . -B build && cmake --build build
./build/ex01_thread_basics
./build/ex02_args_and_ref
./build/ex03_lifecycle
./build/ex04_pthread

bash tests/run_tests.sh       # 一键验收（先于实现写定的就是它）
```

核对要点（与 `tests/run_tests.sh` 的断言一一对应）：

- `ex01`：槽位 55/210/465/820 精确；4 个 worker id 互不相同且都不同于主线程；
- `ex02`：值参后 x=1、引用参后 y=99、指针参后 z=7；
- `ex03`：joinable 1→0；detached 线程把计数置 1；
- `bad_01`：以 abort 结束且出现 `terminate called`；
- `ex04`：取回 `pthread result = 42`；
- `ex05`：独立计数总和恰为 1000000；共享计数 ≤ 1000000（实测常在 50 万~85 万间）。

> 验证记录（测试先行）：验收脚本先于实现写定，首跑构建阶段判红（passed=0）；实现后全绿（passed=7），复跑稳定；构建 `-std=c++11 -Wall -Wextra` 零警告。ex05 共享计数四次实测为 799360、819639、509958、634065——只断言上界，不断言确切值。环境 Ubuntu 24.04 / GCC 13.3，日期 2026-10-23。
