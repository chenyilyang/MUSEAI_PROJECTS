# 第 4 章 练习参考答案（第三部分）

## 练习 1

- **(a) relaxed**。这里只有计数器自己在被读写，不借它发布任何其他数据——需要的是 fetch_add 的原子性（不丢更新），顺序捎带毫无用武之地。选更强的序只会白白付指令开销。这正是 ex01 的写法。
- **(b) 发布方 release、订阅方 acquire**（ex03 的原题）。关键在于数据是普通变量：必须靠标志的序把"写数据"与"读数据"钉成先后关系——release 保证置旗之前的写不被重排到旗后，acquire 保证读数据不被提前到看见旗之前，两者在同一原子变量上相遇构成同步关系。只用 relaxed 时，x86 上可能蒙混过关，ARM 上就是偶发读半成品。
- **(c) seq_cst（默认）**。理不清依赖时用最强序买推理简单：所有 seq_cst 操作有全局统一顺序，不必逐对论证 happens-before。性能不敏感的前提下这是正当选择，而不是偷懒——内存序优化的收益要拿得出 profiler 证据才值得冒推理错误的风险。

## 练习 2

出错时序（初始 g_seats = 1):

```
线程1: load → 1（>0，决定订）
线程2: load → 1（>0，决定订）     ← 两人都基于"还有座"的旧事实下的决定
线程1: fetch_sub → 0，返回 true
线程2: fetch_sub → -1，返回 true ← 座位变负数，超卖完成
```

两步各自原子，但"检查"与"扣减"之间的缝里状态已变——这与第 3 章"检查与等待之间的缝"是同一类错误：**复合逻辑的原子性不会由单步原子性自动拼出来**。

修法一（CAS 循环，乐观重试）：

```cpp
int cur = g_seats.load();
while (cur > 0 && !g_seats.compare_exchange_weak(cur, cur - 1)) {
    // CAS 失败时 cur 已被回写为最新值，循环复查
}
return cur > 0;
```

修法二（先扣后验，用返回值裁决）：

```cpp
int before = g_seats.fetch_sub(1);
if (before > 0) return true;    // 扣之前确实有座
g_seats.fetch_add(1);           // 超卖了：把票号还回去
return false;
```

修法二的要点是裁决依据必须是 fetch_sub 返回的**旧值**（那一瞬间序列化的真相），而不是再去 load 一次。注意回滚后计数短暂为负是可接受的中间态，前提是所有读者都走同一套协议。

## 练习 3

见 `ex03_run_once.cpp`（已编译验证，连跑三次：init runs = 1、8 个线程都读到 config = 42，退出码 0）。

要点：抢资格用 compare_exchange_strong（单次裁决不能容忍虚假失败，否则两个人都以为自己该等对方）；没抢到的人不能直接返回——必须等到状态变 2（acquire 读到)，因为"有人在初始化"不等于"初始化已完成"；初始化者最后用 release 置 2，把其对普通变量 g_config 的写一并发布出去。这道题是 ex03 发布-订阅与 CAS 的合练。标准库另有 `std::call_once` 干这件事，工程中优先用它；手写一遍是为了看清它内部必然长什么样。

## 练习 4

见 `ex04_ticket_dispenser.cpp`（已编译验证：tickets = 8000, unique = yes，退出码 0）。

fetch_add 返回的是**操作前的旧值**，且整个"读旧值+加一"是一步原子操作：每个调用者拿到的旧值天然互不相同（序列化点唯一），不需要先查再改、没有缝。它相当于在硬件层面把练习 2 里两步合成一步——凡是"领号"语义（序号、偏移、槽位索引），fetch_add 都是首选。

## 练习 5

(a) CAS 重试的角度：N 个线程高频 CAS 同一个变量时，每次只有一个成功，其余全部失败重来；争抢越凶，有效吞吐反而越低（重试风暴），而 mutex 会让失败者睡下排队、把 CPU 还给持锁者，稳态吞吐更高。缓存行的角度：两个无关的原子变量若落在同一条 64 字节缓存行上（false sharing，伪共享），两个核各改各的变量也要反复抢夺整条缓存行的所有权，乒乓往返——明明没有逻辑竞争，性能却像有竞争一样差；解法是把热点变量按缓存行对齐隔离（C++17 有 hardware_destructive_interference_size，本教程基线下手工填充对齐即可）。

(b) 自旋锁的等待方式是**占着 CPU 空转**。核数够时无妨：持锁者在另一个核上跑，很快释放。但线程数超过核数时，可能出现：持锁线程被调度器挂起（时间片用完），而自旋者们正占满所有核疯狂空转——持锁者想回来释放锁，却抢不到 CPU，只能等自旋者的时间片耗尽。一把锁的释放被拖上毫秒级，链式反应下整个系统像死锁一样停滞（这叫锁的"护航/优先级反转"类问题）。mutex 的等待是睡眠让行，不存在这种互抢。这就是为什么自旋锁只配出现在"临界区极短且线程数受控"的底层场合，用户态业务代码默认 mutex。
