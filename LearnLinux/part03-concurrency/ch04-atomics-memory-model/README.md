# 第 4 章 原子操作与内存模型入门（第三部分 · 并发与多线程）

## 本章目标

学完这一章，你应该能做到：

- 用 `std::atomic` 的 load/store/fetch_add/CAS 完成单变量的无锁同步，并说清它与"普通变量+运气"的本质区别；
- 用 atomic_flag 拼一把自旋锁，并说清它的适用边界；
- 理解内存序的三档（relaxed、acquire/release、seq_cst），能为发布-订阅场景正确选序；
- 读懂无锁栈的 CAS 循环，并知道 ABA 与内存回收这两道工业级难题的存在。

**前置知识**：第 1~3 章。本章是入门定位：内存序只讲到"能正确选、能说清为什么"，内存模型的完备理论不在本教程范围内。

**本章文件**：示例在 `examples/`（4 个），验收测试在 `tests/run_tests.sh`（测试先行），练习在 `exercises.md`，参考答案在 `solutions/`。

## 1. atomic：把单个变量的读-改-写压成一步

第 1 章的病根是 `++counter` 三步可被插队。第 2 章用锁把三步圈起来。本章换一条路：`std::atomic<T>` 的 `fetch_add` 等复合操作由硬件指令一步完成（x86 的 `lock xadd` 一类），天生不可分割。还有一层更根本的区别：

> 普通变量的并发读写有一方写就是**数据竞争 = 未定义行为**；对同一个 atomic 的并发操作，是标准**定义良好**的行为。

`ex01_atomic_counter.cpp` 在同一程序里并排跑两个版本（都是 4×250000）:

```
atomic counter = 1000000 (expected 1000000), 11 ms
mutex counter  = 1000000 (expected 1000000), 120 ms
```

（作者 2 核环境实测；你机器上倍数会不同，量级关系通常成立。）atomic 快一个数量级的原因：不上锁就不用睡、不用醒、不必在争抢时进内核排队，一条指令干完。但别把结论读过头：atomic 只会做**单变量**的几种固定动作（读、写、加、CAS……），一旦要"同时改两个变量还保持一致"，它无能为力——那仍是锁的地盘。

注意 ex01 给 fetch_add 传了 `std::memory_order_relaxed`：纯计数只用得上原子性，不需要借它捎带任何可见性。这个参数是本章第 4 节的主角。

## 2. CAS：无锁结构的母机

`compare_exchange`（CAS）的语义一句话：

```cpp
bool ok = x.compare_exchange_weak(expected, desired);
// 若 x == expected：x = desired，返回 true；
// 否则：expected 被回写为 x 的当前值，返回 false。
```

"比较并交换"一步原子完成，于是可以搭出统一的无锁套路：**读旧值 → 在本地算新值 → CAS 抢占；失败就带着被回写的新值重试**。第 5 节的无锁栈、练习的票号与 run-once 都是这个套路的变奏。weak 与 strong 的区别：weak 版允许"明明相等却失败"（虚假失败，硬件 LL/SC 的特性），但在循环里反而更高效——反正要重试；脱离循环的单次判断（如练习 3 抢初始化资格）用 strong。

`atomic_flag` 是 CAS 家族的极简成员：只有 test_and_set（置位并返回旧值）与 clear，且是唯一**保证无锁**的原子类型。`ex02_spinlock.cpp` 用它拼自旋锁：抢不到就原地循环重试。验收依旧精确 1000000，但用法边界必须刻住：**临界区极短、线程数不超过核数**时自旋才划算；线程多于核数时，持锁者可能正等着你让出 CPU，而你却在空转抢 CPU——越忙越死。mutex 抢不到会睡下让路，这才是默认选择。

## 3. 内存序入门：原子性之外的可见性

有个容易混淆的点：**原子性 ≠ 可见性顺序**。atomic 保证单个变量的操作不可分割，但当线程 A 先写普通变量 `data`、再置原子标志 `flag` 时，线程 B 看到 `flag` 已置起的瞬间，能保证也看到新的 `data` 吗？编译器与 CPU 都会重排指令，答案取决于你给标志选的**内存序**（memory order）:

| 内存序 | 保证 | 典型用途 |
|---|---|---|
| `relaxed` | 只保证本变量的原子性，不捎带任何顺序 | 纯计数、统计（ex01） |
| `release`（写）/ `acquire`（读） | release 之前的写不许越过它到后面；acquire 之后的读不许跑到它前面。两者在同一变量上相遇即构成"同步"：发布者先前的一切写，对订阅者全部可见 | 发布-订阅（ex03) |
| `seq_cst` | 默认档：全局单一顺序，最强、最易推理、也最贵 | 拿不准时的默认值 |

`ex03_publish_subscribe.cpp` 就是发布-订阅的最小形态：发布者写 4 个普通 int，再以 release 置旗；订阅者以 acquire 盯旗，旗起后读数据，验收其值与总和（1110）完整无误。

一条实务警告：若把 ex03 的序换成 relaxed，在 **x86 上多半仍跑得对**——x86 是强内存模型，硬件帮你兜了底；但 **ARM 是弱序模型**，旗与数据的可见顺序可能真的错位。车载 SoC 以 ARM 为主：在 x86 工控机上测通、在 ARM 座舱上偶发读到半成品配置，是这类 bug 的经典剧本。内存序不是学究洁癖，是跨平台的生死线。

## 4. 无锁栈：CAS 循环的完整形态与诚实边界

`ex04_lockfree_stack.cpp`（Treiber 栈）把本章收官：头指针是唯一的原子变量，push/pop 都是第 2 节的 CAS 循环。4 线程并发入栈 1000 件再并发抢空，件数与总和（500500）守恒——无锁结构的正确性可以这样验。

但请注意示例里两个"故意不做"，它们都是工业级的深水区，本章点名留账：

- **pop 出的节点不 delete**。某线程正握着旧头指针算下一步时，节点若被别的线程释放，它下一步就是 use-after-free。正经解法是 hazard pointer、epoch 回收或 RCU——每种都是一整套机制；
- **ABA 问题**：线程读得头指针 A，正要 CAS 时，A 被弹出、又有一个**地址同为 A** 的节点被压回，CAS 看见"还是 A"便误以为"没变过"，实际拓扑早已天翻地覆。本例节点只进不出（不回收不复用），ABA 暂不发作；一旦开始复用内存就必须正面处理它。

以及一句立场：**无锁 ≠ 无等待 ≠ 必然更快**。高争抢下 CAS 失败重试会互相踩踏（重试风暴），缓存行在核间乒乓；锁在重争抢时反而更稳。工程顺序永远是：先用锁写对、测出热点，再考虑把热点换成无锁——不要反过来。

## 示例代码：构建、运行与验收

```bash
cd examples
cmake -S . -B build && cmake --build build
./build/ex01_atomic_counter
./build/ex02_spinlock
./build/ex03_publish_subscribe
./build/ex04_lockfree_stack

bash tests/run_tests.sh
```

核对要点（与验收断言对应）：

- `ex01`：atomic 与 mutex 两行都是 1000000；耗时只看量级（你的机器上倍数不同是正常的）；
- `ex02`：自旋锁版计数精确 1000000；
- `ex03`：订阅者收到 `111 222 333 444`、总和 1110——一个数字都不能差；
- `ex04`：popped = 1000、popped sum = 500500，并发进出后守恒。

> 验证记录（测试先行）：验收脚本先行写定，首跑构建判红（passed=0）；实现后全绿（passed=5），验收套件另复跑三次全绿，ex03、ex04 各单独连跑 10 次零失败；`-std=c++11 -Wall -Wextra` 零警告。ex01 实测 atomic 11 ms vs 细粒度 mutex 120 ms（2 核 VM）。环境 Ubuntu 24.04 / GCC 13.3，日期 2026-10-23。
