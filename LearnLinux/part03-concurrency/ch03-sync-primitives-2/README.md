## 1. 从"抢"到"等"：为什么需要条件变量

上一章解决的是**抢**（多人同时摸数据）。这一章是**等**：消费者发现队列是空的，该怎么办？最土的办法是循环检查（忙等）：CPU 全速空转烧电，而且检查的那个标志本身还是共享数据，又得配锁或原子。正确的姿势是**睡下，让有活时有人叫你**——这就是条件变量（condition variable）：

> `wait` = 原子地"释放锁 + 睡下"；`notify` = 叫醒一个（或全部）睡着的线程，被叫醒者重新拿到锁再继续。

"原子地释放锁并睡下"是精髓：它堵住了"刚检查完还没睡下、通知就来了"的缝隙（第 5 节的反例正是死在这条缝上）。

## 2. 条件变量三件套与谓词纪律

条件变量从不单独使用，它永远和另外两件东西绑在一起：

1. **一份共享状态**（谓词），如 `bool ready`、队列内容——这是**事实**；
2. **保护这份状态的 mutex**；
3. **条件变量本体**——这只是**提醒**。

等待方的标准写法（背下来）：

```cpp
std::unique_lock<std::mutex> lk(m);
cv.wait(lk, [&] { return /* 谓词：状态已满足 */; });
```

这一行等价于 `while (!谓词) cv.wait(lk);`。为什么必须循环、不能用 if？因为**虚假唤醒**（spurious wakeup）是标准允许的：没有人 notify，你也可能醒来。醒来先查谓词、没满足就接着睡，是唯一的正解。另一个非用 unique_lock 不可的理由就在这里：wait 睡下时要解锁、醒来时要重新上锁，锁的归属要在等待者与条件变量之间交接——lock_guard 没有这身段。

通知方的标准写法：**先在锁内改状态，再 notify**（notify 本身可以在解锁后发）。顺序反了（先 notify 后改状态），被唤醒者查谓词扑空又睡回去，通知等于白发。

`ex01_condvar_handoff.cpp` 是一次双向交接（worker 报到 → 主线程发令），验收对四行日志的**顺序逐字断言**——顺序不是靠运气排出来的，是被谓词的因果链锁死的：主线程的第二行必须等 `ready` 成立才打得出，worker 的第三行必须等 `go` 成立。

## 3. 生产者-消费者：有界队列与关闭协议

`ex02_bounded_queue.cpp` 是全书要反复回访的标准形态。结构要点：

- **两个条件变量分工**：`notEmpty_` 只叫消费者，`notFull_` 只叫生产者。合成一个也写得对，但每次通知都要 notify_all 广播、被叫醒的人查完谓词还得睡回去（惊群），精准唤醒更省；
- **有界 = 反压**：容量满时生产者同样睡下。无界队列在"生产快于消费"时不是更安全，而是把问题转嫁给内存——队列无限涨到 OOM。容量就是系统的一道保险丝；
- **关闭协议**：生产者全部收工后 `close()`：先置 `closed_` 状态，再 **notify_all**（这里用 notify_one 会漏人：没被叫到的消费者永睡、主线程 join 挂死）。消费者在"已关闭且取空"时收到 false 才退出——**存量必须取完**，这正是日志库"退出前刷完尾部日志"的原型。

实测：2 生产者（1..500 与 1001..1500）+ 2 消费者，总量 1000 件、总和 750500 分毫不差，队列水位打满到容量上限 4——生产者确实被反压按住过，而不是一路狂奔。

## 4. POSIX 信号量：自带状态的计数器

`ex03_posix_sem.cpp` 换一种工具干限流：6 个任务抢 3 张许可。POSIX 信号量（`sem_init/sem_wait/sem_post`）是一个**带等待队列的整数计数器**：wait 在计数 >0 时减一通过、=0 时睡下；post 加一并唤醒一个等待者。实测并发水位恰为 3，从未越界，6 个任务全部完成。

把它与条件变量对照，本章最重要的一条认识浮出来：

> **信号量自带状态（计数），条件变量不带状态（通知发过即消失）。**

所以信号量**没有丢失唤醒问题**：post 先于 wait 发生，计数会把这次 post"记账"，后来者直接通过。条件变量的通知则是一次性的，错过就是错过——这正是它必须外挂谓词状态的原因。代价在另一边：信号量只知道"还有几个名额"，表达不了"队列非空且未关闭"这类复合条件；而且它没有锁的"所有权"概念——任何线程都能 post 唤醒，包括不该唤醒的人，灵活与危险同源。C++11 标准库没有信号量（C++20 的 `std::counting_semaphore` 在第 6 章专题登场）。

## 5. 反例复盘：丢失唤醒

`bad_01_lost_wakeup.cpp` 把第 1 节那条缝撑开给你看，两个病灶缺一不可：

1. 等待方**裸 wait**（无谓词）：把全部命运押在"通知一定晚于我开始等"；
2. 通知方**抢先 notify**：worker 还在做准备（睡 300ms）时主线程就发了通知——此刻无人等待，通知落空。

随后 worker 安心睡下，主线程在 join 上永久挂住（验收用 timeout 收尸，退出码 124 即"判过"）。对照 ex01 的免疫机制：状态 `ready/go` 先立好，通知哪怕早到，等待方凭谓词版 wait 一查状态已满足、直接通过——**事实不会迟到，提醒才会**。

## 示例代码：构建、运行与验收

```bash
cd examples
cmake -S . -B build && cmake --build build
./build/ex01_condvar_handoff
./build/ex02_bounded_queue
./build/ex03_posix_sem
timeout 3 ./build/bad_01_lost_wakeup   # 预期挂死，退出码 124
```

核对要点（与验收断言对应）：

- `ex01`：四行日志顺序逐字一致；

- `ex03`：completed = 6、max concurrent ≤ 3（实测恰为 3）；
- `bad_01`：必须挂死（timeout 退出码 124）——反例的"通过"就是挂住。
